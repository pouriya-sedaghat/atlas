# مرحلهٔ پنجم Atlas: توقف بادوام محافظ و تشخیص محدود I/O

تاریخ گزارش: ۲۰۲۶-۱۰-۲۹، منطقهٔ زمانی تهران. زمان داخل artifactها UTC است. این مرحله import کامل ایران را تکرار نکرد و runtime قبلی ایران را ارتقا نداد. وضعیت ردشدهٔ [مرحلهٔ چهارم](ATLAS-STAGE-4-FA.md) و تمام شواهد آن حفظ شده است؛ هیچ انتشار عملیاتی انجام نشده است.

## نتیجه

| مورد | نتیجهٔ ثبت‌شده |
|---|---|
| build و typecheck کل پروژه | موفق |
| آزمون‌های محلی | ۱۳۶ موفق، ۴۰ آزمون وابسته به محیط skip |
| آزمون‌های builder در محیط PostgreSQL | ۳۰ موفق، شامل شش آزمون واحد |
| سناریوهای سرتاسری تازه با PBF ساختگی | ۱۰ موفق |
| سناریوهای خطا و بازیابی محافظ | شش موفق |
| پایش سرویس قبلی در آزمون محدود I/O | ۴۸ درخواست، صفر خطا |
| پذیرش سراسری ایران | تکرار نشده و همچنان باز است |

در سناریوهای سرتاسری نهایی، ۸۴ probe به سرویس fixture قبلی بدون خطا انجام شد؛ این probeها سرویس ایران یا کاربران واقعی نیستند. در آزمون اتصال پایشگر به محافظ، یک endpoint ساختگی عمداً HTTP 503 داد. همان یک خطا باید ثبت می‌شد و به توقف unit آزمایشی می‌انجامید؛ آن پاسخ، قطعی سرویس اصلی نیست.

## توقفی که پس از crash هم باقی می‌ماند

پایشگر، token تلاش جاری را پیش از ارسال HTTP می‌گیرد. پس از خطا، ابتدا تطابق root، pipeline، فایل پیکربندی، DSN کنترل، unit و نسخهٔ guard/data/queue را بررسی می‌کند. سپس تحت همان قفل تراکنشی admission و completion، مشاهده و SHA آن را ثبت، job را ناموفق، نتیجه‌نویسی و heartbeat تلاش را fence و اجازهٔ کار سنگین مشترک با intake را بسته نگه می‌دارد. شمارندهٔ شکست فقط یک بار افزایش می‌یابد؛ تکرار همان رویداد idempotent است.

توقف unit پس از commit رخ می‌دهد. بنابراین crash میان ثبت خطا و stop، اجازهٔ تکرار import را باز نمی‌کند. deadline اسلات عمداً `infinity` است و reaper جدید، incident تأییدنشده را جدا هم بررسی می‌کند. این انتخاب با [معنای timestampهای ویژه در PostgreSQL](https://www.postgresql.org/docs/17/datatype-datetime.html) تطبیق داده شد؛ انقضای معمول lease جای تأیید cleanup را نمی‌گیرد.

token منقضی، job تمام‌شده یا root/pipeline متفاوت اجازهٔ توقف worker جایگزین را ندارد. واحد عملیاتیِ مجاز، نام ثابت سازنده است؛ unit جایگزین فقط با الگوی مشخص و control DB ساختگی پذیرفته می‌شود. تغییر فایل DSN یا نسخهٔ runtime نیز binding را می‌شکند. این‌ها ابزار اپراتور مورد اعتمادند و هویت مستقل از مالک مشترک Unix ایجاد نمی‌کنند.

## بازیابی با کنترل هویت

بازیابی، خاموش‌شدن unit و هویت هدف ثبت‌شده را بررسی می‌کند: کانتینر، image، volume، system identifier پایگاه، نشان مالک و build identity. فقط importer/Martin دارای label دقیق همان تلاش متوقف می‌شوند. LOGIN و password نقش‌های import/tile/QA همان تلاش غیرفعال و CONNECT آن‌ها لغو می‌شود؛ دیتابیس و داده پاک نمی‌شوند.

اتصال‌های مدیریتی اکنون `application_name` شامل شناسهٔ job و token دارند. این کار، اتصال مدیریتی همان تلاش را حتی در دیتابیس postgres قابل تفکیک می‌کند. بازیابی فقط اتصال نقش‌های مشخص در دیتابیس candidate و اتصال‌های مدیریتیِ نشان‌دار همان تلاش را می‌بندد. اتصال ناشناس حفظ می‌شود و اجازهٔ شروع کار بعدی را بسته نگه می‌دارد. صرف ارسال سیگنال کافی نیست؛ نبود session دوباره بررسی می‌شود. مبنا: [سیگنال‌دهی backend](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADMIN-SIGNAL) و [کنترل LOGIN/password](https://www.postgresql.org/docs/17/sql-alterrole.html).

پس از تأیید همهٔ این شروط، incident تأیید و admission آزاد می‌شود. همان candidate ناموفق باقی می‌ماند. اجرای دوبارهٔ recovery، worker دیگر یا اسلات مالک جدید را متوقف/آزاد نمی‌کند. SIGTERM معمولی بدون incident، رفتار قبلی cancellation/retry را حفظ کرده است.

هفت آزمون جدید PostgreSQL، restart و expiry، تکرار هم‌زمان، token قدیمی، root/pipeline/مشاهدهٔ نامعتبر، مسابقه با completion، بازیابی و مجوز تغییر شواهد را بررسی کردند. شش سناریوی واقعی systemd/Docker/PostgreSQL نیز binding واحد اشتباه، crash پس از commit، target تغییریافته، بستن backendهای import/admin، حفظ اتصال ناشناس، لغو credential و مسیر واقعی HTTP را پوشش دادند. دو incident و رویدادهای commit/ack واقعی در [شواهد](evidence/2026-10-29-guard/README.md) ثبت شده‌اند.

## نتیجهٔ آزمون محدود I/O

سازندهٔ واقعی خاموش ماند. در دیتابیسِ ازقبل‌ناموفق ایران، فقط aggregate جدید حسابرسی اجرا شد: ۱۵ ثانیه baseline، یک query فقط‌خواندنی با سقف ۲۰ ثانیه، سپس ۱۵ ثانیه پایش پس از آن. query با SQLSTATE `57014` در حدود ۲۰٬۰۰۴٫۶۴۵ ms به سقف عمدی رسید؛ حسابرسی کامل یا پذیرش candidate از آن ساخته نشد.

| بازهٔ آغاز درخواست | درخواست | خطا | بیشینهٔ HTTP مشاهده‌شده |
|---|---:|---:|---:|
| baseline | ۱۴ | ۰ | ۳۹۲٫۲۵۹ ms |
| خواندن محدود | ۱۹ | ۰ | ۳۲۵٫۵۵۲ ms |
| پس از خواندن | ۱۵ | ۰ | ۲۲۹٫۴۶۹ ms |

در نمونه‌های کل بازه، کانتینر داده حدود ۱۴۵٬۶۹۸٬۸۱۶ بایت خواندن و ۱۴٬۱۷۶٬۲۵۶ بایت نوشتن ثبت کرد. این شمارنده‌ها فعالیت پس‌زمینهٔ PostgreSQL را هم شامل می‌شوند؛ query آزمایشی transaction فقط‌خواندنی داشت و محتوای عوارض را تغییر نداد. device فیزیکی مجازی و لایهٔ dm یک I/O را در دو لایه گزارش می‌کنند و با هم جمع نمی‌شوند. بیشینهٔ event-loop delay ابزار حدود ۳۷٫۹۱۳ ms بود.

PSI مربوط به I/O بالا رفت؛ محدودیت عمدی cgroup نیز می‌تواند در این فشار سهم داشته باشد. نوع storage فیزیکی و بار میزبان همچنان معلوم نیست. این مشاهدهٔ کوتاه، علت timeout قبلی، ظرفیت هم‌زمان، latency در اجرای چندساعته یا جداسازی منابع را ثابت نمی‌کند. مهلت پنج‌ثانیه‌ای HTTP و سقف‌های عملیاتی SQL/I/O افزایش نیافتند. اولین خطای serving در ابزار تشخیص، خواندن را متوقف می‌کند.

## اصلاح ابزار آزمون و حدود تحویل

یک اجرای آزمون قدیمی صف، به‌علت lease یک‌ثانیه‌ای fixture و تأخیر I/O به `lease_lost` رسید؛ لاگ ۲۹ موفق/یک ناموفق حفظ شده است. lease همان fixture به ده ثانیه رسید؛ آزمون‌های expiry همچنان deadline سرور را صریح منقضی می‌کنند. این تغییر، افزایش مهلت عملیاتی نیست. فرض زمانی دیگری دربارهٔ صف‌گذاری توسط unit تازه‌راه‌اندازی‌شده نیز با enqueue صریح جایگزین شد. گزارش‌های نهایی از fixtureهای تازه پس از این اصلاح‌ها هستند.

سورس محافظ آماده و در VM روی fixtureهای واقعی آزموده شده است؛ **در runtime قدیمی ایران فعال نشده است**. راهنمای [ارتقا و recovery](../infra/atlas/builder/serving-guard.md) مرزها و پیش‌نیازها را مشخص می‌کند. ارتقا باید با drain، schema و runtime هماهنگ انجام شود. محافظ برای commit اختیارش به control DB قابل دسترس نیاز دارد؛ partition، خرابی دیسک و توقف کامل میزبان هنوز تضمین نشده‌اند. cleanup عمومیِ همهٔ failed/abandonedهای تاریخی، GC، گراف artifact/reuse، همهٔ موتورهای release، gateway/وب/نشست و handoff/rollback همچنان باقی‌اند.

گام بعدی، آزمون بلندمدتِ کنترل‌شدهٔ رقابت I/O با همین محافظ و سپس پذیرش دوبارهٔ ایران است؛ یک اجرای کوتاه بی‌خطا نباید جای شرط بدون‌اختلال را بگیرد.
