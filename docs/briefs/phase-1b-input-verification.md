## Review evidence and decisions

The designated-VM review inspected sealed run `b42600fb-369a-4499-9711-79ada46754bb`, stored under `2026-11-18` in `Asia/Tehran`. It reports matching fingerprints for Iran PBF and all 554 POLYs. A bounded observer found 27,026,513 nodes, 3,398,894 ways and 99,081 relations in the Iran PBF. It reported zero missing way-node references and missing relation-member occurrences of 283 nodes, 39,605 ways and 898 relations. The observer reached EOF in 79.6 seconds with about 259 MiB peak RSS. These measurements provide comparison evidence. Full semantic extraction, independent Osmium reconciliation, GEOS topology and complete extraction costs require implementation evidence.

| Decision | Approved Part 1B behavior |
| --- | --- |
| Decoder | Generated proto2 messages from pinned official OSM schemas plus bounded framing, decompression and semantic checks |
| Object output | Versioned JSON Lines compressed with Zstd, with exact integers, explicit metadata presence and ordered collections |
| Reference severity | Missing way nodes block verification. Missing relation members produce typed warnings |
| Boundary policy | Provider longitude/latitude plane, preserved section order and subtraction roles, GEOS topology and explicit polar/antimeridian fixtures |
| Batch severity | Any blocking required POLY finding holds the entire batch, including a POLY-only region |
| Empty data | Valid empty PBFs and POLY-only runs retain their verification results and have `build_eligible=false` |
| Resources | One verifier, one CPU, 2 GiB RAM, one-hour execution limit, 20 GiB per-attempt disk cap and 60 GiB total verification storage cap |
| Handoff | One immutable, digest-addressed successful result per verification attempt, after fenced publication and final eligibility checks |

The initial policy covers faithful extraction and input verification. Part 1C will choose coverage assembly, reconcile regional overlaps and build a separate PostgreSQL/PostGIS candidate using the approved handoff.

## Operator flow and durable lifecycle

Reuse the existing authenticated panel and PostgreSQL control plane. Show acquisition runs grouped by their stored retrieval date, including two runs on the same date. The operator selects one exact sealed run and sees its ID, frozen catalog revision, selected PBFs, boundary-only regions, recorded provider exceptions and integrity state before requesting verification. Apply server-side authorization, CSRF protection and actor-attributed audit events. Manual and Automatic acquisition share this verification flow.

Introduce an attempt lifecycle separate from the per-artifact transfer `Attempt`. In one transaction under the acquisition run lock, validate sealed eligibility, accept an operator-scoped request key and persist the frozen verification inputs. A replay returns the accepted attempt, including after a later input invalidation. A distinct intentional request creates a new verification attempt. Persist the artifact IDs, typed kinds, region IDs, paths, accepted lengths and SHA-256 values, catalog digest, approved exception scope, policy and tool versions and operator. Keep this snapshot immutable.

Use a dedicated verifier process with a read-only inbox mount and separate writable verification storage. Run one active verification with durable progress, execution generations and leases. Track input-invalid, unsupported-profile, operational/resource-failed, verified, and verified-with-warnings outcomes with structured reasons. A valid boundary-only or empty-data result may complete verification while remaining ineligible for a build. Retain generation-specific failure reports and completed output history.

A retry after an operational failure can reuse the attempt and original snapshot under a new fenced generation. Intentional re-verification creates a separate attempt. The worker must renew its claim during long decoding and reference passes. It must be possible to recover after a killed child, worker restart or Compose restart without another generation publishing the wrong output. Failed attempts must explain completed and incomplete checks. At most one successful result can be registered per attempt.

## Exact input identity, storage and resource accounting

Open inbox paths descriptor-relative from the trusted root, rejecting symlinks at every component and requiring a regular final file. Copy bounded bytes into a worker-owned private spool and compare the copied byte count and SHA-256 with the frozen input. Decode and independently inspect that stable spool throughout the attempt. A path replacement or source write during the copy must either produce the original matching bytes or fail integrity. Keep the spool inaccessible to the web and intake writer. Hashing the input and decoding a separately reopened mutable inbox path is insufficient.

Use the 1A source URL, dated PBF pin, retrieval instant and upstream checksum result as provenance. Preserve the distinction between provider MD5 verification and local SHA-256 identity. A POLY can pass with the recorded SHA-256 when no provider checksum exists. Compare the artifact set with the frozen run before processing. Frozen approved provider exceptions are explicit coverage records. Integrity errors block the attempt and preserve the acquisition history and accepted fingerprints.

Configure the verifier for one CPU, a 2 GiB process/container memory ceiling, a one-hour execution deadline, 20 GiB total per-attempt working and output space, and a 60 GiB verification-root budget. Enforce the memory ceiling using a cgroup `memory.max` of at most 2,147,483,648 bytes covering the verifier and its children. Record effective CPU/memory settings, memory and swap observations, and before/after OOM event counters. Interpret transient `memory.peak` excursions using documented kernel accounting semantics and retain the measured values. Judge a resource failure from enforcement, execution or allocation failure and OOM evidence. Include spools, reference indexes, compressed outputs, failure generations and staging in accounting. Retained outputs count toward the root cap. Reserve space in PostgreSQL under a shared capacity lock and account for intake reservations when both use the same filesystem. Preserve the existing 20 GiB filesystem free-space reserve and 1A inbox budget. Enforce limits while streaming and while indexes or files grow. A failed reservation, memory ceiling, child timeout or output cap creates a visible operational/resource failure and releases the active verifier slot.

Keep accepted output history during the pilot. Clean only abandoned scratch whose generation and publication records prove it is unused. Review disk use before a second complete verification. If the approved limits cannot complete faithful extraction, return the measured gap for review and keep the recorded limits until revised. The decoder, all subprocesses and index caches must fit the process budget together. Production verification uses recorded local inputs and requires no source download.

## Supported PBF profile and extraction

Use generated proto2 messages as the authoritative source decoder. Vendor the official `osmpbf/osmformat.proto` and `osmpbf/fileformat.proto` with their license and source provenance. Reviewed official file blob IDs are `311e8cef6d25db5883e35eff0c729cb73a9a38f0` and `7392143c46bf301a2452e06065e8ae8590bed163`, respectively. Verify these identities when preparing the files. Record the upstream revision, schema hashes, compiler and compatible protobuf runtime versions and a reproducible generation command. Pin installed dependencies and verifier image.

Support OSM v0.6 snapshots with ordinary nodes, dense nodes, ways and relations, using raw or zlib blobs. Recognize the required schema and dense-node flags and report every required and optional feature. Unknown required features, history/deletion shapes and unsupported compression produce an explicit unsupported-profile result. Unknown optional names alone do not invalidate a file. Preserve the original PBF and describe the supported schema in the output. If an unhandled data-bearing field prevents faithful extraction, report that capability gap and withhold verification. Auxiliary block types that the PBF specification permits readers to skip may be bounded, recorded and skipped.

Enforce a BlobHeader length below 64 KiB and decompressed Blob length below 32 MiB. Bound serialized input lengths, cumulative expansion, protobuf object overhead and wall time. Check complete framing to EOF, required fields, exact compressed-stream termination and declared raw size. Validate positive coordinate/date granularities, string-table indexes, parallel arrays, delta reconstruction and scalar ranges, metadata cardinalities, dense-tag delimiters and recognized relation member types. Check primitive groups and type ordering using actual objects. Full-stream inspection includes untagged objects. Unsorted valid snapshots can use the disk-backed identity index, with ordering recorded. Apply snapshot identity checks independently of any header ordering claim.

Reconstruct coordinates as `offset + granularity × decoded_integer` in integer nanodegrees. Preserve block precision parameters and their encoded presence in a bounded block table. Reconstruct timestamps from integer ticks and date granularity in milliseconds, retaining exact source values and field presence. Preserve explicit zero changeset/UID and empty contributor strings as present values. Record the provider redaction policy as provenance. Missing metadata is represented separately. Dense metadata arrays may be absent or aligned to the node count under the accepted profile. Preserve the distinction between missing Info/DenseInfo and absent child fields. Proto2 repeated fields do not expose an empty-versus-absent distinction, so the output contract must state the source semantics it preserves.

Extract all typed IDs and all tags, ordered way node references, optional position-aligned locations on ways, and ordered relation members with type, ID and role. Include a stable source ordinal and block association. Store full-width identifiers and exact nanodegree coordinates as decimal strings in JSON. Preserve ordered tag pairs and duplicates. Store a missing-field indicator separately from each available source value. Valid string data must round-trip exactly. Invalid text encoding or data the approved output cannot represent produces an explicit finding.

Use `objects.jsonl.zst` with a versioned record schema and bounded compression buffers. Write block metadata as bounded records in a separate sidecar if needed. Use deterministic content serialization and fixed compression settings, keeping attempt timestamps outside content records so re-verification can compare semantic content digests. Record compressed size and SHA-256, uncompressed record-stream digest, count and schema version. Reconcile counts against the full scan and a small independent output reader. JSON Schema and tiny fidelity fixtures belong in Git. Parquet is deferred to an evidence-based format revision.

Block malformed/truncated input, duplicate typed identities or conflicting versions inconsistent with a snapshot, out-of-range coordinates, and invalid required semantic relationships. A semantically valid empty snapshot receives a valid-empty finding and remains build-ineligible. Record header replication fields, actual object timestamp ranges, actual node bounds, per-type object and tag counts and bounded relation/tag summaries. Keep source content timestamps, HTTP Last-Modified, intake time and verification times distinct.

## Complete reference checks and independent reconciliation

Build a disk-backed typed-ID index for each extract and query source reference batches against it. Keep unresolved references in the extracted object records. For way-to-node and relation-to-node, relation-to-way and relation-to-relation, report total inspected references, missing reference occurrences, distinct missing typed targets, affected source objects and bounded samples. These quantities must be calculated independently and retain full-width identities. Indexes must support sparse high IDs within the disk and memory caps.

Missing way nodes are blocking. Missing relation members yield typed warnings and can coexist with `build_eligible=true` when all other checks pass and every selected PBF is nonempty. Record the warning counts in regional and batch manifests. Attribute a missing target to an extraction edge only when evidence establishes that cause. Regional timestamps and reference completeness remain per input. Cross-region merge and conflict decisions belong to 1C.

Run pinned `osmium fileinfo --extended --json` on the same stable spool and compare node, way and relation counts and declared findings. For a valid spool with no node bounds that the pinned inspector cannot render in JSON, use a narrowly selected reconciliation adapter running full-file `--extended --get=data.count.nodes`, `--get=data.count.ways` and `--get=data.count.relations` against the same spool. Require each command to finish successfully and return exactly one valid nonnegative decimal count. Persist the commands, raw results and adapter version, compare all counts, and represent absent bounds explicitly. Other inspector failures retain their failure classification. A count disagreement blocks successful verification. A failed mandatory reconciliation is an operational or unsupported-profile failure and cannot be treated as a clean cross-check. Use `check-refs -r` as supplementary evidence only when ordering and measured resources permit. Its exit code 1 covers missing references and processing errors, so diagnose its output explicitly. The authoritative complete reference result comes from the bounded typed-ID pass.

## POLY geometry and batch severity

Use a pinned GEOS library through Django's GEOS bindings. Preserve source bytes, decimal coordinate tokens, header text, section identifiers and order, and inclusion/exclusion roles. Use the catalog ID as region identity. Interpret the format in the provider's longitude/latitude coordinate plane, with finite longitude in [-180, 180] and latitude in [-90, 90]. Honor format-permitted implicit ring closure in a derived validation geometry and report it. Preserve raw ring closure as encoded.

Build the filter area using valid inclusion and subtraction sections in their defined order. Validate individual rings, nonempty area, exclusion containment against the included coverage available at that point, and the composed polygon/multipart geometry. Overlapping valid inclusion sections may compose through a recorded union. Preserve the component checks and diagnose failures before any composition operation. Repeated consecutive coordinates are retained and counted, and are warnings if the ring and composed area remain valid. Orientation alone is an informational finding. Never silently repair a self-intersection or a failed exclusion using a geometry-cleaning operation.

Use the published multipart sections on either side of the antimeridian as given. Preserve -180 and +180 as distinct coordinates in this validation plane. Antarctica's published rectangle from -180 to +180 and -90 to -60 is a valid full-longitude latitude band in this policy. Do not apply shortest-edge longitude unwrapping to it. Test interior points on both sides of the globe and outside the latitude band. Test Fiji, Russia and US/Alaska as multipart coverage and South Africa's exclusion. Distinguish this planar validity result from any later spherical or projected engine interpretation.

The whole frozen batch is verified only when every non-excepted required POLY has passed syntax, ring, containment and composed-coverage checks. This applies to boundary-only regions as well as selected PBF regions. Any unresolved invalid topology or coverage ambiguity blocks batch verification and build eligibility. Persist regional reports and counts even if another region blocks. Do not create a new exception to turn a topology failure into a passing result. Existing frozen, approved missing-POLY exceptions retain their documented scope. If the full corpus reveals a new provider geometry case, report its file digest, reason and proposed policy change for review. A fully verified POLY-only run completes with `build_eligible=false`.

## Manifest contract and publication

Use schema version `1` for batch, regional and object-record contracts and a named versioned verification policy. Keep a separate output root with this layout:

```text
verification/<retrieval-local-date>/<run-id>/<verification-id>/manifest.json
verification/<retrieval-local-date>/<run-id>/<verification-id>/regions/<safe-region-key>/manifest.json
verification/<retrieval-local-date>/<run-id>/<verification-id>/regions/<safe-region-key>/objects.jsonl.zst
```

Stage generation-specific output privately. Keep failure reports identifiable by attempt and generation. Use safe collision-free region keys with a mapping to original IDs. The batch manifest must include retrieval and verification IDs, catalog digest, frozen input fingerprint, schema/policy and tool versions, timestamp semantics, selected and boundary-only coverage, exceptions, completed checks, totals, reasons, outcome, eligibility, source attribution and regional manifest paths and SHA-256 values. Regional manifests include exact source identities, timestamp fields, object/tag counts, reference findings, boundary results and every output path, encoding, count, size and digest.

Derive the frozen input fingerprint from deterministic ordered artifact IDs, region IDs, kinds, paths, lengths and SHA-256 values plus catalog digest and approved exception scope. Exclude operator identity and attempt timestamps from it. Hash actual serialized manifest bytes separately. Keep ID values and counts round-trip safe. Version the encoding and reject unsupported manifest versions explicitly. Bound manifest, sample, error and audit sizes. Include representative JSON Schema and sample manifests during implementation.

Fence finalization with generation ownership. Persist the complete intended output identity, sync files, publish without overwriting accepted paths and sync directory entries. Register the full output set and batch manifest in one database transaction after publication can be reconciled. Just before registration, lock the acquisition run and verify that it remains eligible, all frozen artifact records still match and no integrity invalidation has intervened. A stale generation, changed snapshot, missing output or integrity failure cannot publish a handoff. A post-registration input invalidation also revokes usable eligibility through the handoff check.

Expose a durable handoff containing run ID, verification ID, manifest schema/policy versions, exact batch-manifest SHA-256 and `build_eligible`. Each attempt has at most one successful result. A retry replay returns it. A later re-verification produces a new attempt and content-comparable outputs. Part 1C will recheck current input eligibility, the batch manifest and every referenced output digest before import. Keep real extracts, manifests, decoded records and runtime logs outside Git.
