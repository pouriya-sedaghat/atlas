**Status** — Draft for Codex design review on the Atlas VM. Part 1A was merged through [PR #1](https://github.com/pouriya-sedaghat/atlas/pull/1) at `3b6323b09b7b7dd987d9dc52e45c647caf4d9eb7`. ## Outcome and operator flow

An authorized operator opens the existing list of intake runs grouped by retrieval date. Within the chosen date, the panel shows the run ID, frozen catalog revision, regions, selected PBFs, POLY-only regions, recorded exceptions and current integrity status. The operator starts verification for one exact sealed run. Manual and Automatic acquisition share this workflow. Multiple runs on the same date remain independently selectable. Keep the action authenticated, permission checked, CSRF protected and audited. Return durable progress and structured per-region findings, with a run-level result and documented retry action.

Use only sealed intake runs with current input integrity. Persist the run ID, catalog digest, exact artifact identifiers, kinds, paths, expected byte lengths and SHA-256 values, reviewed provider exceptions, verifier and policy versions, and requesting operator with the verification attempt. Treat the list as frozen once the attempt begins. The same action or retry replay must recover its existing attempt. An intentional re-verification gets a distinct attempt ID against the same inputs. The previous records and bytes remain available for audit. Keep verification outcome separate from acquisition state. A verification failure must retain the original ingestion and integrity history. Before registering a result as eligible, confirm the run is still eligible and that the frozen input identity still matches the durable records.

A verification worker should reuse the PostgreSQL control plane, admin permissions, audit conventions and safe storage practices from 1A. Evaluate a dedicated worker process with a read-only inbox mount and a separate writable verification directory. Keep potentially long scans out of the web request and intake scheduler. Start with one active verification and budget CPU, memory, scratch space, concurrent I/O and wall time. Verification operates on the locally acquired bytes and recorded provenance. Measure impact on the existing intake worker and verify recovery after a killed process or Compose restart. Part 1C owns the automatic import into a separate PostGIS candidate. Part 1B exposes the durable handoff that it will consume.

## File identity and verification execution

- For each expected artifact, open a safe path below the inbox and check length and SHA-256 against the 1A records. Preserve source URL, pinned URL and recorded upstream checksum outcome. Local SHA-256 identifies stored bytes and the provider checksum is a distinct check. A POLY without a provider checksum can pass using the recorded SHA-256 and content checks. A missing file, change in bytes, mismatch with the frozen artifact list or ineligible required artifact blocks verification. A frozen, approved POLY exception is recorded with its reason and scope.
- Review how to ensure the decoder sees the exact bytes that were hashed even if a path changes during inspection. Prefer a bounded worker-owned spool whose bytes are hashed against the frozen identity, then passed to the decoder. An alternative must prove the same content identity across every pass. Never change the source inbox. Bound parser buffers, data expansion, object/reference indexing, log output and scratch use. A process crash, resource exhaustion or unsupported decoder capability has a distinct result from invalid source content and cannot produce a successful verification.
- Record progress and a worker lease or fencing generation. Publish completed result files without overwriting older attempts. Reuse the 1A pattern of persisting intended output identity, syncing staged bytes and directories, and reconciling publication before marking history complete. On restart, resume valid staged work or restart the same attempt safely with its original snapshot. Expose outputs only after all manifest and output fingerprints are registered. Failure reports must state which inputs were checked and which checks could not finish. A blocked attempt cannot feed a build.

## PBF inspection and full extraction

For each selected PBF, stream the complete snapshot to EOF, including untagged objects. Evaluate Osmium/libosmium or pyosmium for the full scan and an independent Osmium count check. A header-only check or geometry export does not meet the requirement. Capture the header and required/optional feature flags, available replication parameters and data timestamp, object timestamp range, bounds from actual nodes, type counts, tag totals and selected bounded tag and relation summaries. Keep download time, HTTP modified time and PBF header timestamps in separate fields. Capture unsupported features and parser limitations as structured findings. The public Geofabrik extracts omit contributor names, user IDs and changeset IDs. Represent absent source fields explicitly.

Produce a reusable, versioned stream of all supported source objects for the eventual PostGIS build. Retain the original PBF as the byte-exact source. The decoded representation must preserve each typed OSM ID, node coordinates at source precision, available source metadata, all tags, ordered way node references, optional locations on ways when present, and ordered relation members with type, ID and role. Respect the distinction between missing fields and source values. Preserve ordering and duplicate entries where they are meaningful, and keep full-width IDs without conversion to floating-point numbers. The review should compare a compressed record stream with an alternative that offers smaller disk usage and a clear compatibility story for 1C. Confirm that the decoder exposes every required field and coordinate precision for the supported source profile. Unsupported input features that prevent faithful extraction block the attempt. Keep all tags and object records in the stream, with bounded summaries and samples in the manifest. Reconcile output row or record counts against the full scan.

Check references per source extract with disk-backed or otherwise measured resource usage. Check way-to-node and relation-to-node, way and relation links. Preserve unresolved references in the extracted object stream and record counts by source and target type, affected object counts and bounded samples. Diagnose processing failure separately from missing references. The `osmium check-refs` command can use the same exit code for both conditions and requires type/ID ordering, so an unchecked exit code cannot determine severity. Preserve object identity by type and ID. For the initial policy, propose that missing way-node references block selected PBFs and missing relation members produce typed warnings. Validate this policy against the Iran extract and record any required change before implementation. An unresolved reference indicates a missing target within the input. Describe an extract edge as the cause only when the available evidence supports it.

Block unreadable data, malformed or truncated input, unsupported required features, snapshot/history shape mismatches, and conflicting versions or duplicate typed IDs inconsistent with the accepted snapshot profile. Show the distinction between whole-file validity and downstream readiness. An input manifest attests the checks performed. Routing, maps and search readiness are later decisions.

## POLY inspection and coverage policy

Interpret each available `.poly` as Geofabrik's extraction boundary in longitude/latitude order. Read all inclusion and exclusion rings and preserve the raw coordinates, ring identities and multipart structure. Evaluate syntax, empty groups, finite coordinates, ring validity, holes and containment, multipart geometry, and antimeridian behavior. Document coordinate bounds and closure semantics for the actual provider files. Choose and benchmark a geometry library for the detailed check and record its version and reason codes. Keep any normalized display geometry as a derived output with traceable rules. Retain the input tokenization and raw bytes for audit. Any normalization around the antimeridian must preserve the region and holes.

Proposed initial policy blocks missing or structurally invalid required POLY inputs without an approved exception. Treat topology failures or representation ambiguity as review findings and withhold build eligibility until the policy approves the affected coverage. Inspect the existing 554 live POLYs as a set before choosing severity for provider-specific geometry. Keep intentional POLY-only regions visible and distinguish them from regions carrying a PBF. A successful POLY-only run may have a verified boundary manifest and must have `build_eligible=false`. Record reviewed exceptions rather than synthesizing coverage or treating a stale panel preview as input.

## Manifest and storage contract

Use a clearly versioned schema and a separate verification output root. Recommended layout is:

```text
verification/<retrieval-local-date>/<run-id>/<verification-id>/manifest.json
verification/<retrieval-local-date>/<run-id>/<verification-id>/regions/<safe-region-key>/manifest.json
verification/<retrieval-local-date>/<run-id>/<verification-id>/regions/<safe-region-key>/objects.<encoding>
```

Use stable safe region keys that preserve a mapping to the original Geofabrik ID. Include the schema and policy versions, verification and retrieval IDs, catalog digest, local date and UTC timestamps, status and eligibility, source attribution, input fingerprint, pinned inputs, parser and geometry library versions, selected PBF regions, boundary-only regions, exceptions, and linked regional manifest paths and SHA-256 values in the batch manifest. Region manifests describe file-level identity and source metadata, coverage, full-scan summaries, reference findings, boundary checks, and extracted output path, encoding, size, count and SHA-256 where applicable. Bound manifest and audit size, with compact summaries and exact reason codes. Full-width OSM IDs in JSON must round-trip without loss. Document which timestamps describe the source, receipt and verification.

Define one stable fingerprint over the frozen input set using deterministic field encoding and ordering. Hash the actual serialized manifest bytes separately. A verified handoff supplies the run ID, verification attempt ID, manifest schema version, manifest SHA-256 and build eligibility. When 1C reads it, it will revalidate the manifest and referenced output digests and check input eligibility. Each verification attempt can produce at most one verified handoff. Prepare representative small fixtures and JSON Schema for the approved format during implementation. Keep real extracted objects, raw artifacts, manifests and operational logs outside Git.

## Acceptance evidence for the implementation brief

- On the designated VM, use an intact sealed 1A run with the live Iran PBF and POLY, Monaco POLY with PBF unselected, and the rest of the frozen POLY catalog. Identify the run by its actual stored date and ID. Show the administrator's selection and trigger, regional results, whole-Iran object counts and sample records, separate timestamp fields, aggregate findings, per-region and batch digests, and a repeat with matching content counts and findings or evidence of the exact policy issue that blocks it. Verify that the original inbox bytes and hashes are unchanged. Report peak memory, scratch and disk usage, scan duration, output sizes and the effect on intake.
- Use controlled fixtures for unreadable or truncated PBF, unsupported required features, digest mismatch, missing expected file, duplicate or conflicting object identity, tags and members with ordering and full-width IDs, absent metadata, missing way node and relation member references, and data timestamp differing from retrieval time. Include multipart boundaries, holes, invalid topology, antimeridian handling, a POLY-only run and a frozen provider exception. Verify that digest mismatch, parser failure and expected coverage failure cannot create build eligibility.
- Exercise authorized and unauthorized panel access, two same-date runs, duplicate clicks and concurrent claims, a crash around output publication, input invalidation during verification, and a successful retry or intentional re-verification. Show that a complete manifest and output remain identifiable on restart and that a partial or superseded claim cannot be used for a build. Test decoding the output using a small independent reader and reconcile counts and ordering.
