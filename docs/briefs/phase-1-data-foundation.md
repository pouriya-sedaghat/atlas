## Purpose and delivery order

Atlas is an independent provider of OpenStreetMap geographic data. Phase 1 establishes a repeatable, auditable path from Geofabrik downloads to verified PostgreSQL/PostGIS releases. An internal probe will exercise dataset routing and session continuity before consumer engines exist. Map, routing, geocoding and reverse geocoding are Phase 2. Consumer-facing contracts belong to Phase 3.

| Part | Deliverable | Review evidence |
| --- | --- | --- |
| 1A | Geofabrik region catalog, administrator panel, manual and scheduled retrieval, durable inbox | VM smoke run with Iran PBF and POLY, a POLY-only region, and restart and failure tests |
| 1B | Administrator-triggered verification by date and run, full OSM scan and versioned manifests | Real sample statistics and fixtures for corrupt inputs, missing references, and boundary edge cases |
| 1C | Automatic build of an isolated PostGIS candidate and automatic database verification | Import reconciliation, end-to-end validation evidence, and serving-load isolation measurements |
| 1D | Automatic release promotion, session pinning, lifecycle controls, and recovery | Concurrent-session cutover, rollback, drain and expiration tests, and an operator runbook |

Codex reviews the brief for each part and reports findings before receiving an implementation prompt. Implement and test approved changes on the designated VM, push a branch to this repository and open a PR with verification evidence. Project review and acceptance of that part precede the next implementation. Keep application source, migrations, test fixtures and operational docs in Git. Runtime inputs, manifests, database files, credentials and production logs belong outside Git.

## Phase 1 architecture

### Control plane and data plane

Use an administrator web application, a background worker with a persistent scheduler, and a PostgreSQL control database for catalog revisions, schedules, jobs, artifacts, audits, releases, and sessions. Start with a small VM deployment with separate application and worker processes, a managed persistent filesystem for the inbox and release artifacts, and distinct roles for administration, downloads, builds and read-only serving. Each release is a new physical PostgreSQL database with PostGIS. Keep the control database independent of release databases. Benchmark resource contention and decide from VM evidence whether the serving and build instances need distinct PostgreSQL clusters or hosts. Limit worker CPU, memory, I/O and disk usage, including scratch space and the capacity needed for the active and incoming releases.

Use stable IDs for catalog revisions, retrieval runs, verification attempts and releases. Each job has a durable state, claim/lease or equivalent, progress and an audit trail. Use transactional job creation where the control database owns both the state change and the job row. When a workflow crosses PostgreSQL DDL or the filesystem, reconcile partial operations after restart. Retried work cannot overwrite a sealed input or publish an incomplete candidate.

### Source, inbox and manual verification

Geofabrik's public catalog defines the hierarchy of areas and public PBF availability. A retrieval run freezes its catalog revision and PBF selection. Request POLY by default for every region in that revision, including those without a selected PBF. A POLY describes the provider's clipping area for display as such in the admin panel. Keep the retrieval time, provider data timestamp and, when available, replication metadata distinct. The same retrieval date can contain multiple runs and different upstream data timestamps.

Group inbox paths by run creation date in the configured Atlas timezone for manual runs and the schedule timezone for automatic runs. Record the applied timezone with each run and persist instants in UTC.

```text
inbox/asia/iran/YYYY-MM-DD/<run-id>/iran.osm.pbf
inbox/asia/iran/YYYY-MM-DD/<run-id>/iran.poly
verification/YYYY-MM-DD/<run-id>/<verification-id>/manifest.json
database/YYYY-MM-DD/<release-id>/README.md
```

Allow deeper region paths. Derive safe local path segments from validated catalog ancestry and preserve the upstream ID in metadata. The database directory holds release artifacts and documentation. PostgreSQL manages its own database storage. Each release README lists the regions with published PBF data, distinguishes polygon-only coverage, and records release ID, input and manifest references, data timestamps, schema version, and OSM source and attribution.

The admin panel groups completed and incomplete runs by local date, showing each region and file status. The operator selects a specific sealed run within a date and starts verification. Verification opens each artifact by its immutable identity, confirms its fingerprint and streams the entire PBF. Preserve original input bytes and retain all available node, way and relation fields, tags, ordered references and relation member roles through a lossless extraction path. Keep the verification manifest bounded. It records provenance, size and checksums, source and retrieval timestamps, parser and schema versions, object counts, bounds, tag and relation summaries, reference diagnostics, polygon validity and the outcome with errors or warnings. The batch manifest pins the per-region manifests and the expected feature coverage. Public Geofabrik PBFs omit OSM contributor user, UID and changeset fields. Evaluate Osmium/libosmium for full scans and reference checks.

Define which anomalies block verification. An unreadable or truncated file, checksum mismatch, or missing expected PBF blocks a build. Assess dangling references at extract edges separately from unreadable data, recording their types and counts. Validate POLY outer rings, holes, and multipart coverage with verified fixtures. Flag unavailable or invalid POLY explicitly. Establish which polygon failures block a release based on its declared coverage. A new verification attempt on sealed input reuses the same fingerprints and records its own outcome.

### Automatic candidate build and verification

Successful intake verification automatically enqueues the candidate build. Bind the build to the verified manifest digest, importer version and migration version. Build in an isolated target, create an Atlas-owned raw schema and required spatial indexes, and use a separate read-only serving role. Store nodes, ways, relations, tags, and ordered references via streaming import and reconcile them against the input manifests. Keep an Atlas-owned schema boundary even if importer software uses its own internal tables.

Specify the policy for overlapping and mixed-vintage extracts before implementing multi-region imports. Treat identifiers as distinct by OSM object type. Deduplicate identical objects and preserve region provenance. Block ambiguous or conflicting overlaps until there is a reviewed reconciliation policy. Prohibit silent coverage regressions when a subset of regions is retrieved. A candidate must satisfy the declared release coverage before promotion, with explicit approval for coverage shrinkage. The part 1C brief will choose how unchanged verified regional inputs are carried forward and how source vintages are represented.

Automatic candidate checks cover PostGIS and schema versions, expected/input versus actual coverage and row counts, spatial column types and SRIDs, declared geometry validity criteria, indexes, permissions and probe queries against recorded fixtures. Preserve raw objects when a derived geometry cannot be formed and record the applicable rejection or warning. Persist the result and README before promotion. A build or verification failure leaves the current serving release available.

### Promotion and session lifecycle

Resolve the active release in the control database when an Atlas data session opens. Persist the chosen release ID with the session and reuse it for all requests until close or expiry. Serialize promotion and new-session admission against the same control record so a session sees a single admissible release even during cutover. Validate candidate reachability through the serving identity before the pointer changes. Assign an explicit publication generation when a build is requested to prevent an older job that finishes late from replacing a newer release. An explicit rollback advances the generation. Keep in-flight requests and live session leases attached to their original release. Use a defined lease renewal and maximum session lifetime policy, include in-flight requests in drain completion, and make the admin view distinguish logical Atlas sessions from PostgreSQL pool connections.

| Admin status | Operational meaning |
| --- | --- |
| Active — current | Default target for new sessions |
| Active — draining | Existing sessions continue, admission is suspended |
| Inactive | Retained release, available for audited reactivation after a readiness check |
| Expired | Terminal release ID with an audit tombstone after required purge evidence |

For the first successful release, set the default pointer. For later automatic promotions, assign new sessions to the verified candidate and drain the former release. Once the drain completes, retain it as inactive for rollback. For an administrator-initiated deactivate or expire on an active release, require a verified, available replacement, either newer or older. Suspend new admissions to the target and wait for logical sessions, requests and target database connections to clear as appropriate. Rollback is a promotion of an eligible retained release for new sessions. Sessions already attached elsewhere retain their routing. Block retirement of the last serviceable active target after bootstrap.

Expiration is irreversible for the target release. Track purge progress separately and mark the release expired only after the agreed scope has been cleared. Before part 1D, agree on database backups, snapshots, WAL, dumps, replicas, shared verified inputs, and whether reconstruction of matching contents under a new release ID counts as recovery. A database drop alone does not establish irrecoverability. PostgreSQL database creation and deletion run outside the control database transaction and require retry-safe reconciliation.

Single-VM acceptance covers a cutover while Atlas remains online, end-to-end probe traffic under a concurrent import, and restart recovery. Host-outage availability depends on the eventual deployment topology. Set measurable error-rate and latency thresholds using the VM baseline before implementation of promotion. Carry source and ODbL attribution into releases and review applicable redistribution obligations before external service.

## Part 1A — implementation requirements

The designated VM review confirmed that GitHub reads and bounded Geofabrik requests worked, including Iran's dated PBF redirect, a dated MD5 sidecar, and sample POLY links. It found Docker Compose and sufficient disk for the Iran smoke run. Registry access, Git push, persistence across restart, and backup coverage were unverified. Larger extracts and PostGIS import capacity require separate measurements. The [initial review brief](https://github.com/pouriya-sedaghat/atlas/blob/0b5d3f27d324640b642ecf5ad78a590642d5552a/docs/briefs/phase-1-data-foundation.md#codex-prompt--review-only) records the original assignment.

### Deployment and pilot limits

- Use Django 5.2 LTS, server-rendered templates, Django authentication and permissions, one application image with separate web and worker processes, and a supported PostgreSQL image for the control database. Pin supported dependency and image versions or image digests. Use Compose on the Atlas VM. Run migrations explicitly and expose health checks for the web service, database and worker. Keep PostgreSQL on the private Compose network. Use distinct service credentials as appropriate and a private HTTPS entry point for the admin panel. A VM-local smoke test may use a loopback-only listener and private access through a tunnel.
- Use configurable persistent bind mounts, with `/srv/atlas/data/postgres` and `/srv/atlas/data/inbox` as VM defaults. Check the mounts, filesystem permissions and space before using them. Keep staging on the inbox filesystem and out of the RAM-backed `/tmp`. Keep secrets in VM-managed files or Compose secrets. Give the worker inbox write access and use a non-superuser application database role. Keep application runtime data out of Git.
- Start with one active retrieval run and at most two concurrent file transfers. Configure pilot limits of 1 GiB per PBF, 2 MiB per POLY, 2 GiB of artifacts per run, a 50 GiB inbox budget including staging, and a 20 GiB filesystem free-space reserve. Account for outstanding reservations and include retries, partial files, and pre-existing bytes in capacity checks. Fail visibly before downloading a known oversized selection. Enforce streaming limits for unknown or misreported lengths. Preserve finalized inputs and metadata throughout 1A. Reclaim unreferenced staging files only after a 24-hour grace period and after checking for a current worker claim or a pending publication record. Decide finalized-artifact retention before broadening data collection. The region tree can still list an extract beyond the pilot budget and must give the reason a retrieval was blocked.

### Catalog and frozen retrieval intent

- Read `https://download.geofabrik.de/index-v1-nogeom.json`. Keep the previously validated revision if refresh fails. Validate unique IDs, parent references and cycles, expected fields and permitted source URLs. Allow optional fields and missing public PBF links. Keep identity based on the upstream ID, including slash-containing IDs and duplicate names. Derive collision-free local hierarchy segments from validated ancestry and keep upstream URL paths independent of local paths. Make the tree searchable and make PBF selection explicit per region. Selecting a parent PBF does not select its descendants.
- Resolve each region's POLY using a verified public region-page URL derived from the provider PBF pattern or a reviewed mapping. Resolve and validate actual links against the public source allowlist. Deduplicate lookups for shared links and cache the mapping per catalog revision. Provider outliers, including missing PBF URLs or ambiguous pages, can use an explicit mapping. A missing POLY may be excepted only when an Atlas project maintainer approves a repo-tracked entry naming the region, catalog applicability, reason and provider evidence. Audit which entry was applied. A normal operator may retry retrieval, while only a reviewed catalog or exception revision may change future intent. A provider outage is a transfer failure.
- At dispatch, freeze the catalog revision, vetted POLY mapping and exceptions, timezone, limit policy and exact PBF selections. Create a POLY intent for every region, even if a URL is unresolved. Retain unavailable selected PBF IDs as blocking issues visible on the run. A refreshed catalog or exception revision applies to a new run. Show stale fallback boundaries with the date of their last successful retrieval. A stale fallback cannot fulfill a new run's POLY intent.

### Launch, scheduling and operator workflow

- Start in Manual mode. An authorized operator can start a Manual run with a stable request key. Replaying a previously accepted manual key returns that run, including after a mode change. A separate intentional launch receives its own run ID.
- Each new Automatic schedule revision stores the activation and expiry dates and times, IANA timezone, explicit UTC offset for each ambiguous wall time, resolved UTC bounds, elapsed interval and saved PBF selection. Default the zone to `Asia/Tehran` and the interval to 24 hours. Accept positive elapsed intervals in whole minutes. Validate each bound independently. Reject nonexistent wall times and require a valid explicit offset for ambiguous ones. The first due occurrence must be at or after the save instant and strictly before expiry. Poll before long catalog work and after the worker settles a run. Validate operational cadence with a 24-hour interval on the pilot VM, including an acceptance test for deliberate misses when the worker or slot is unavailable.
- Let `A` be activation in UTC, `E` expiry and `I` the elapsed interval. The planned instant of occurrence `n` is `D = A + n × I`, starting at `n = 1` and keeping instants strictly before `E`. Display planned and actual instants in the saved zone. The eligible admission window starts at `D` and ends strictly before `min(D + I, D + 24h, E)`. A late admission keeps the original cadence. Use UTC arithmetic across DST changes and calculate the inbox date from actual admission time in the saved run zone.
- Serialize admission, schedule save or replacement, switching to Manual, and retrieval queue claims using the existing `Control` row lock. Read the effective clock and revision under the lock. Previously queued manual, legacy and operator-retry work has priority. Admit an Automatic occurrence only when the retrieval slot is available and a validated catalog exists. In one transaction, create the run as `RUNNING`, freeze the validated catalog and saved PBF selection, create its artifact intents and advance occurrence progress. Use the schedule revision ID and planned UTC instant as the durable occurrence identity and enforce uniqueness in PostgreSQL. Reuse slot release when only prepared or paused publication remains. Run provider and filesystem actions outside the admission transaction.
- Persist a cursor for the last resolved occurrence and derive the latest nominal slot with integer elapsed arithmetic. After delayed polling, admit at most the latest eligible occurrence. Keep a due occurrence open while the slot or catalog is unavailable until its window closes. Record closed unserved occurrences as `Missed`, using one bounded audit range for a contiguous set with first and last planned instants, count and reason. Use the observed blocker where known and a generic elapsed-window reason otherwise. Close elapsed windows and supersede remaining slots when the operator replaces the schedule or switches to Manual. Previously admitted runs continue with their frozen settings.
- At expiry the panel shows `Expired` and no next occurrence, including while the worker is offline. The selected mode stays Automatic until the operator saves a new Automatic revision or switches to Manual. Keep waiting, next planned, admitted, missed and superseded outcomes distinguishable in the panel and audit trail. Show the planned occurrence and actual admission time on the run page. Preserve authorization and CSRF protection for state-changing actions.
- Upgrade the existing review baseline from schema `0002`. Migrate existing schedules as legacy one-offs and preserve schedule and run IDs, statuses, request keys, catalog references, artifact paths and existing queued work. Replace `Run.schedule` with a protected foreign key, backfill `Run.scheduled_for` from the linked one-off `due_at`, and use the per-run planned instant for new and historical display. A still-pending legacy one-off remains eligible once during its original 24-hour window subject to the same available-slot and queue-precedence policy. The operator can replace it with a recurring revision or switch to Manual. Document the upgrade with web and worker stopped, and a matched database and inbox restore path for rollback after multiple runs refer to a revision.

### Upstream pins and download validation

- Before streaming a selected PBF, resolve its latest URL to a supported dated Geofabrik URL and durably record the requested URL, resolved URL and resolution time. Fetch the MD5 sidecar for the exact dated filename, then persist the expected byte length, expected MD5, HTTP validators and completed pin time before reading the file body. A strong ETag, when present, is used with `If-Match`. Check response status, validators when provided, actual byte count and MD5. Compute SHA-256 for the local identity. Require a supported dated target and an unambiguous matching checksum record. Missing sidecars are retried within a bounded policy against the same dated target, then leave the PBF incomplete. A malformed sidecar, mismatched length or checksum, or changed validator fails the attempt and is reported. A retry keeps the dated target once selected and keeps all established pins. If the pinned target disappears or changes, a new run must resolve a new target. Pins are per artifact and do not imply a common source instant across the run. Keep wall-clock retrieval time, HTTP `Last-Modified` and any data timestamp extracted directly from the PBF as separate fields. Leave the PBF content timestamp unset until a parser reads it. Dated filenames and the external replication feed are separate provenance fields.
- For POLY, freeze the verified URL in the run. Fetch the published `.poly` URL directly and stream its response bytes into the region's inbox file. For example, [Iran's published endpoint](https://download.geofabrik.de/asia/iran.poly) supplies the contents of `iran.poly`. Use the region page for link discovery and preserve the response bytes as the raw artifact. Apply available strong validators to the bounded transfer and verify a provider sidecar when advertised or configured. If a sidecar is unavailable, record that status and accept the file after basic format and completeness checks and a local SHA-256. Record which attempt finalized these bytes because upstream POLYs can be mutable. Full polygon topology checks start in 1B.
- Restrict downloads and lookups to approved public Geofabrik HTTPS URLs. Validate the initial request and every redirect, enforce allowed host, port, path and file type per request, and cap redirect count, HTTP timeouts, response sizes and retries. Keep input paths below the approved inbox root and stage each attempt at a unique path.

### Publication, restart recovery and sealing

- Use one artifact per run, region and file kind. Persist a publication intent binding the intended path, verified length and SHA-256 to the staging artifact. Flush the verified staged file. Serialize finalization under the artifact lock and recheck the current worker claim or fencing generation. Publish on the same filesystem with an atomic no-overwrite operation, sync the relevant directory entries, then mark the artifact complete. Adopt an already published file only if it matches the committed intent. A mismatched file is an integrity incident. Record it and preserve the accepted fingerprints and evidence. A stale worker must be unable to finalize or replace another attempt.
- On restart reconcile staged publication, a published file with an unfinished metadata update, and complete records with missing or altered bytes. Use bounded background integrity checks to avoid tying web startup to the total inbox size. Reuse a matching published file after validation. Surface a missing or changed completed artifact as an integrity failure that blocks downstream eligibility, retaining original history and sealed metadata. Never repin a completed artifact. Keep unfinished failed artifacts visible and provide safe, idempotent retry for eligible failures. A run is sealed only when each selected PBF is durably complete and each POLY is durably complete or has its frozen approved provider exception. An unexpected missing POLY or selected PBF keeps the run incomplete. Future part 1B uses only sealed runs that still pass integrity checks.
