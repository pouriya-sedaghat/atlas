# مرحلهٔ ششم Atlas: اجازهٔ ساخت وابسته به پایش زنده

تاریخ: ۲۰۲۶-۱۰-۲۹؛ زمان artifactها UTC است. سازندهٔ آزمایشی به runtime جدید ارتقا یافت، اما اجازهٔ شروع ساخت **بسته** و unit سازنده **خاموش** است. هیچ import کامل تازهٔ ایران، تغییر نسخهٔ عمومی یا انتشار عملیاتی انجام نشد. منبع ایران همچنان فقط baseline آزمایشیِ پذیرفته‌شده است.

## نتیجهٔ واقعی

| بررسی | نتیجه |
|---|---|
| build و typecheck محلی | موفق |
| آزمون‌های محلی | ۱۳۶ موفق، ۴۸ وابسته به محیط skip |
| آزمون builder با PostgreSQL واقعی | ۳۸ موفق؛ شامل هشت مورد جدید admission/watch |
| سناریوهای سرتاسری PBF ساختگی | ۱۰ موفق؛ ۸۴ probe ساختگی بدون خطا |
| خطاهای محافظ با systemd/Docker/PG | شش موفق؛ پس از اصلاح پایش نیز تکرار شد |
| مرگ واقعی پایشگر با SIGKILL | توقف بادوام، لغو backend و credential، بدون retry |
| کپی و ارتقای runtime در حالت paused | ۱۶۲ درخواست سرویس قبلی، صفر خطا |
| آزمون طولانی‌تر I/O | **رد شد**؛ ۱۲۲ درخواست، یک TimeoutError و یک HTTP 200 دیررس |
| بررسی پس از توقف بار | ۲۳ کاشی متمایز، صفر خطا، محتوای یکسان |

این نتایج معیار «عدم اختلال حین ساخت ایران» را نمی‌بندند. سلامت پس از توقف بار، شکست زیر بار را خنثی نمی‌کند.

## قرارداد اجازهٔ شروع

schema جدید، `admission_enabled=false` و `serving_watch_required=true` دارد. worker عادی مجوز تغییر این سیاست را ندارد. حالت paused پیش از reconcile و hash کردن PBF بررسی می‌شود؛ اجرای worker در این حالت تنها کارهای نگهداری/فنس‌کردن لازم را انجام می‌دهد و ساخت تازه نمی‌گیرد.

برای claim، هم اجازهٔ مدیر و هم شاهد زندهٔ سرویس قبلی لازم است. پایشگر پس از پاسخ سالم، محدود به پنج ثانیه و با محتوای ثابت، lease سی‌ثانیه‌ای را تمدید می‌کند. token پایشگر به همان attempt متصل می‌شود. پایشگر جایگزین یا پاسخ سالمِ دیررس نمی‌تواند فقدان پایش تلاشِ درحال اجرا را پنهان کند. pause مدیر شروع بعدی را می‌بندد؛ لغو فوریِ تلاش سالم جاری نیست.

از دست رفتن watch، هنگام heartbeat یا بررسی claim در تراکنش ثبت می‌شود؛ این مسیر پیش از retry ناشی از lease-expiry قرار دارد. علت `atlas.serving-watch-loss/1` است و به‌عنوان خطای HTTP ساختگی ثبت نمی‌شود. incident، تلاش را ناموفق و اسلات سنگین را تا بازیابی معتبر نگه می‌دارد. timer مستقل هر ده ثانیه incidentهای ثبت‌شدهٔ همین root/pipeline را بازیابی می‌کند؛ timer جای heartbeat یا ناظر خارجی میزبان نیست.

در آزمون SIGKILL نخست، فقدان lease حدود ۲۹٬۹۵۰ ms پس از kill مشاهده شد. گزارش نهایی collector وجود ندارد؛ تعداد کل درخواست و خطای آن **نامعلوم/null** است. فقط checkpoint آماده‌شدن باقی است. آزمون پس از اصلاح ابزار نیز جداگانه ثبت شده است. هیچ‌کدام unit سازندهٔ واقعی را متوقف نکردند.

استثنای `init --fixture-unguarded` فقط برای provider ساختگی و نام کنترل‌دیتابیس محدودِ آزمون پذیرفته می‌شود. manifestهای E2E این استثنا را صریح ثبت می‌کنند؛ پاس‌شدن آن‌ها ادعای watch عملیاتی نیست.

## شکست آزمون طولانی‌تر و اصلاح پایش

آزمون فقط‌خواندنی، روی دیتابیسِ ازقبل‌ناموفق ایران اجرا شد؛ نه روی candidate تازه و نه به‌عنوان پذیرش QA. بارِ برنامه‌ریزی‌شده ۵۴۰ ثانیه بود، اما در حدود ۱۶۴ ثانیه پس از آغاز خواندن متوقف شد. هفت query با سقف ثابت بیست ثانیه به `57014` رسیدند؛ query هشتم هنگام قطع آزمایش خاتمه یافت. هیچ query کاملِ موفق از آن گزارش نشده است.

baseline چهارده درخواست بدون خطا داشت؛ بازهٔ خواندن ۱۰۸ درخواست و یک TimeoutError داشت. بازهٔ recovery داخل همین اجرای قطع‌شده نمونه‌ای ندارد؛ «صفر از صفر» شاهد سلامت نیست. بررسی جداگانهٔ بعدی ۲۳ کاشی متمایز را سالم دریافت کرد. کانتینرهای قبلی همان شناسه و زمان آغاز را دارند و restart/OOM ثبت نشده است.

یک پاسخ تبریز در بزرگ‌نمایی ۱۰ با HTTP 200 در **۱۶٬۹۹۶٫۸۹۴ ms** تکمیل شد؛ TimeoutError بعدی تهران حدود **۸٬۶۹۹٫۳۳۰ ms** دیده شد. بیشینهٔ event-loop delay ابزار حدود **۱۵٬۷۴۵ ms** بود. در توقف event loop، callback مهلت پنج‌ثانیه‌ای نیز ممکن است دیر پردازش شود؛ بنابراین status موفق، رعایت deadline را ثابت نمی‌کند. گزارش خام حفظ شده و ارزیابی مشتق‌شده دو مشاهدهٔ نامعتبر از نظر deadline را ثبت می‌کند. عدد یکِ `errors` در گزارش خام، شمار خطاهای HTTP/transport ابزار همان اجراست، نه قبولی همهٔ deadlineها.

ابزار اکنون elapsed time را مستقل از AbortSignal می‌سنجد. پاسخ موفقِ بیش از پنج ثانیه یا محتوای تغییریافته، با حفظ `wire_status` به مشاهدهٔ نامعتبر تبدیل می‌شود و watch را تمدید نمی‌کند. آزمون HTTP محلی با توقف واقعی event loop و آزمون مرز deadline ثبت شده است. اجرای اولیهٔ آزمون تکمیلی به اشتباه در مسیر join خودِ harness متوقف شد؛ fixture دقیقاً شناسایی، ساکت و ناموفق نگه داشته شد. پس از اصلاح، شش سناریوی محافظ و SIGKILL دوباره اجرا شدند؛ خطای harness به‌عنوان قبولی مخفی نشده است.

runtime مهرشدهٔ سازنده دست‌کاری نشد. نسخهٔ اصلاح‌شدهٔ پایشگر به‌صورت bundle مستقل با hash فایل‌ها نصب و آماده‌شدن/بسته‌شدن پاک آن در برابر job واقعیِ paused بررسی شد. این bundle با symlinkهای صریح فقط به apps و وابستگی‌های همان runtime متصل است؛ با کپی قدیمی ابزار در runtime اشتباه گرفته نشود. مسیر و هویت دقیق در `observer-bundle.json` آمده است. pipeline سازنده و digest ابزار پایش دو هویت جدا دارند؛ پیش از هر شروع آینده، همین bundle تأییدشده باید استفاده شود.

فشار I/O افزایش یافت؛ cgroup نیز عمداً I/O را محدود می‌کند. شمارنده‌های sda و dm دو لایهٔ همان مسیرند و جمع نمی‌شوند. نوع storage و وضعیت میزبان فیزیکی معلوم نیست. وقفهٔ event loop می‌تواند با توقف زمان‌بندی VM سازگار باشد، اما علت را ثابت نمی‌کند. ریشهٔ مشکل همچنان باز است و deadlineها برای قبولی آزمون افزایش نیافته‌اند.

## وضعیت باقی‌مانده و اقدام بعدی

pipeline جدید `3c429f78191c2286aa881e31af17765e59cde728d2086e876b7f4cafd539460e` و job ایران `f0c512214b74a289fafdfad6d3e26e6da19820a13b5f77be25e7720dc65944ad` است: queued، صفر attempt و بدون manifest. تلاش ناموفق قدیمی با همان هویت و وضعیت باقی است. حافظه و I/O واقعی کانتینر داده کنترل شد؛ حدود ۱۹۱٫۵ GiB فضای آزاد ثبت شد. فایل‌های معمول runtime فقط‌خواندنی‌اند، hardlink ندارند و symlinkهای همان runtime خارج از آن نمی‌روند. امضاکننده و worker ورودی فعال‌اند. registry انتشار در control DB این نصب وجود ندارد؛ مقدار null در snapshot به معنی «نسخهٔ منتشرشدهٔ بررسی‌شده» نیست.

گام بعد، تشخیص توقف زمان‌بندی VM و مسیر storage از سمت hypervisor/میزبان و طراحی جداسازی یا مهار قابل‌اندازه‌گیری است. تا رفع و آزمون این شرط، بار سنگین تکرار نمی‌شود. هیچ software guard محلی، هنگام توقف کامل VM یا عدم دسترسی به control DB نمی‌تواند SLA بدون‌قطعی را تضمین کند. پس از رفع، پذیرش ایران باید با معیار ثابت، پوشش عوارض، SQL/HTTP و ثبت شکست‌های واقعی دوباره اجرا شود. سپس انتقال مؤلفهٔ مهرشده، همهٔ موتورهای لازم، gateway/وب، نشست قدیمی، handoff/rollback و GC قابل ادامه‌اند.
