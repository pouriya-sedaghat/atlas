# پیشنهاد معماری ورود داده و انتشار چندنسخه‌ای Seyra

تاریخ: ۲۰۲۶-۱۰-۲۶ — وضعیت: پیشنهاد برای توافق؛ پیاده‌سازی و استقرار نشده است.

## مبنا و دامنه

خواسته‌های تثبیت‌شدهٔ کاربر: حذف Tegola، استفاده از PBF ایران در مرحلهٔ حاضر، تحویل دستی فایل در مسیر مشخص، پردازش و انتشار خودکار نسخه‌های عادی، ارجاع موارد غیرعادی به تأیید انسانی، حفظ سرویس هنگام ساخت/انتشار، جلوگیری از تداخل نسخهٔ کاربران و نگهداری تعداد محدودی از نسخه‌ها.

سخت‌افزار، اندازهٔ واقعی PBF، منبع دریافت، بار هم‌زمان، دورهٔ انتشار و عمر مجاز نشست هنوز تعیین نشده‌اند. بنابراین این سند عدد ظرفیت، مدت import یا SLA تأییدشده ارائه نمی‌کند. اعداد احتمالی نگهداری صرفاً نمونهٔ سیاست‌اند.

## ۱. اصلاح مفاهیم و تصمیم پایه

Tegola در سورس حاضر سرویس کاشی برداری است. نمایش وب را MapLibre انجام می‌دهد و جست‌وجو، مسیریابی و POI از موتورهای دیگر می‌آیند. حذف Tegola یک تغییر در لایهٔ کاشی است؛ کیفیت کل نقشه به منبع، مدل داده، قواعد طبقه‌بندی، generalization، style، فونت و آزمون‌های صحت هم وابسته است.

پیشنهاد پایه: PostGIS برای ذخیره و پردازش فضایی، SQLهای محدود و نسخه‌دار برای تولید MVT، Martin برای سرو کاشی، MapLibre برای نمایش، و یک gateway ثابت برای API و مسیرهای نسخه‌دار. Martin از PostGIS function source پشتیبانی می‌کند؛ `pg_tileserv` نیز گزینهٔ معتبر مقایسه است. تصمیم نهایی باید با داده و workload یکسان سنجیده شود؛ برتری عددی از روی زبان برنامه‌نویسی یا معرفی ابزار ادعا نمی‌شود. [Martin Function Sources](https://maplibre.org/martin/sources-pg-functions/)، [pg_tileserv Usage](https://access.crunchydata.com/documentation/pg_tileserv/latest/usage/).

برای Martin فقط منابع صریح و مجاز منتشر شوند؛ کشف عمومی جدول‌ها/توابع و مسیرهای مدیریتی در مرز عمومی فعال نباشد. نقش دیتابیس حداقل دسترسی را داشته باشد. نمونه‌های مستندات جایگزین بازبینی امنیتی SQL نیستند. توابعی که از جدول داده می‌خوانند با volatility صحیح، عموماً STABLE، تعریف شوند. [Martin Configuration](https://maplibre.org/martin/config-file/)، [PostgreSQL Function Volatility](https://www.postgresql.org/docs/16/xfunc-volatility.html).

ساخت tile server یا parser پایهٔ OSM از صفر در دامنهٔ پیشنهادی نیست. منطق اختصاصی محصول در مدل داده، قرارداد لایه‌ها، کیفیت، سیاست انتشار و مدیریت release قرار می‌گیرد. نسخهٔ پایدار ابزارها و سازگاری CPU/PostGIS هنگام اجرا تثبیت می‌شود؛ قابلیت‌های شاخهٔ توسعه و beta به‌صورت خودکار مبنا قرار نمی‌گیرند.

## ۲. «تمام featureها» چگونه تعریف می‌شود؟

سه تعهد مستقل لازم است:

1. **حفظ کامل ورودی:** همهٔ node، way و relation موجود در فایل، شامل اجزای بدون tag، شناسه‌ها، tags، ترتیب nodeهای way و اعضا/roleهای relation و metadata موجود حفظ شوند. نبود metadata در منبع با مقدار ساختگی پر نشود. فایل PBF اصلی نیز به‌صورت تغییرناپذیر نگهداری شود.
2. **ساخت دادهٔ مشتق:** هندسه‌ها، دسته‌بندی و لایه‌های قابل استفاده ساخته شوند. رابطهٔ پیچیده، عارضهٔ فاقد هندسه و tag ناشناخته با علت در گزارش بماند؛ چیزی به‌علت خارج بودن از catalog از دادهٔ خام حذف نشود.
3. **نمایش و قابلیت محصول:** نمایش هر لایه و پشتیبانی معنایی هر نوع relation/tag با ماتریس پوشش تعریف شود. وجود tag در دیتابیس تضمین پشتیبانی آن در موتور مسیریابی یا UI نیست.

حفظ کامل محدود به محتوای فایل دریافت‌شده است؛ نمی‌توان عوارض غایب از extract یا صحت میدانی جهان واقعی را با import تضمین کرد. ارجاعات ناقص مناطق مرزی باید اندازه‌گیری و بر اساس سیاست منطقه بررسی شوند.

مدل پیشنهادی PostGIS برای هر release:

- `osm_raw`: primitives و روابط اصلی؛ ID از نوع bigint، tags به‌شکل JSONB، موقعیت nodeها در WGS84 و بدون گردکردن اضافی؛ ترتیب اعضا و ارجاعات محفوظ.
- `features`: هندسه‌ها و دادهٔ موضوعی مشتق، همراه با lineage تا primitiveهای منبع و گزارش تبدیل/رد هندسه.
- `tiles`: جدول‌های generalization و توابع صریح MVT با index مناسب، min/max zoom و قواعد نمایش ثبت‌شده.

موتور importer می‌تواند بر osm2pgsql flex تکیه کند، اما schema خام، بخشی قراردادی از محصول است و نباید به جدول‌های موقت و داخلی importer وابسته باشد. در صورت استفاده از flex، مسیر tagged و untagged هر دو باید پوشش داشته باشند. در بستهٔ فعلی `--drop` دادهٔ middle را پس از import حذف می‌کند؛ بنابراین وضعیت فعلی آرشیو کامل primitives در PostGIS محسوب نمی‌شود. [osm2pgsql Manual](https://osm2pgsql.org/doc/manual.html).

tile نسخهٔ آرشیوی دادهٔ خام نیست: clipping، تبدیل مختصات، quantization و generalization بخشی از نمایش‌اند. اصل هندسه جدا می‌ماند و قواعد ساده‌سازی قابل آزمون است. حذف دلخواه ردیف‌ها با LIMIT برای سریع شدن، جایگزین طراحی لایه و aggregation نمی‌شود. [PostGIS ST_AsMVTGeom](https://postgis.net/docs/ST_AsMVTGeom.html)، [PostGIS ST_AsMVT](https://postgis.net/docs/ST_AsMVT.html).

## ۳. واحد انتشار، مجموعهٔ کامل نقشه است

هر release یک بستهٔ منطقی مشخص دارد:

| جزء | نیاز نسخه‌ای |
|---|---|
| PBF و گزارش پذیرش | checksum، منبع ادعاشده/تأییدشده، محدوده و زمان snapshot |
| PostGIS | دیتابیس مستقل و freezeشدهٔ خام، مشتق و tile |
| مسیریابی | graph و تنظیمات ساخته‌شده برای همان release |
| جست‌وجو | index و normalization مخصوص همان release |
| POI | store یا سرویس متصل به همان release |
| assets | TileJSON، styles، sprites و fonts مشخص و تغییرناپذیر یا content-addressed |
| manifest | نسخهٔ schema/API/pipeline/catalog، digest imageها و artifactها، گزارش کیفیت و امضا |

Valhalla، Photon و Overpass در این پیشنهاد فعلاً حفظ می‌شوند؛ تعویض آن‌ها تصمیمات جداگانه می‌خواهد. به‌روزرسانی فقط PostGIS درحالی‌که این سرویس‌ها دادهٔ قبلی دارند، شرط سازگاری کاربر را تأمین نمی‌کند. استفادهٔ دوباره از یک artifact تنها با اثبات یکسان بودن وابستگی‌های آن مجاز است.

`source_sha256` شناسهٔ ورودی است و `release_id` شناسهٔ بستهٔ منتشرشده. یک PBF با pipeline، schema یا style متفاوت می‌تواند release متفاوت داشته باشد. idempotency بر ترکیب ورودی و build specification تکیه می‌کند. ثبت زمان و امضا نباید باعث دوباره‌سازی بی‌دلیل ورودی یکسان شود. شناسهٔ کامل برای تطبیق استفاده شود؛ نمایش کوتاه hash صرفاً برای UI است.

ثابت بودن release، به معنی ثابت ماندن منطقی داده است؛ log، lock و translog موتورهایی مانند Photon ممکن است تغییر کنند. صحت اولیهٔ artifact، snapshot قابل بازیابی و هویت دادهٔ سرویس باید از وضعیت کاری قابل نوشتن تفکیک شوند.

## ۴. مسیر تحویل دستی و پردازش خودکار

نمونهٔ مسیر پیشنهادی لینوکس، هنوز ایجاد نشده است:

```text
/srv/seyra/ingest/incoming/<submission_id>/iran.osm.pbf.part
/srv/seyra/ingest/incoming/<submission_id>/source-manifest.json
```

پس از پایان کپی، ابزار تحویل فایل را در همان filesystem به نام نهایی تغییر می‌دهد و submission را با marker نهایی ready می‌کند. اگر کپی بین filesystemهاست، ابتدا کپی کامل و sync انجام می‌شود و فقط سپس marker نهایی منتشر می‌شود. ثابت ماندن اندازه یا گذشت چند ثانیه به‌تنهایی نشانهٔ پایان upload نیست.

watcher اعلان سریع می‌دهد و reconciliation دوره‌ای صف از دست رفتن event پس از restart را جبران می‌کند. کنترلر job بادوام ثبت می‌کند، فایل را claim و به quarantine مدیریت‌شده منتقل می‌کند و یک snapshot خصوصی و قابل اعتماد از bytes می‌سازد. فایل source پس از پذیرش قابل ویرایش نیست؛ checksum حین تحویل و پیش از مصرف کنترل می‌شود. symlink، مسیر خروج از محدوده و فایل ویژه رد شوند؛ digest تکراری و job تکراری دوباره import نشوند.

صف اولیه می‌تواند در control database پیاده شود؛ افزودن Kafka یا مجموعهٔ بزرگ سرویس‌ها بدون نیاز اندازه‌گیری‌شده ضروری نیست. claim، lease، fencing token و state transition باید جلوی اجرای دوبارهٔ مؤثر توسط worker قدیمی را بگیرند. هم‌زمانی ورود و ساخت با بودجهٔ منابع محدود می‌شود؛ بیش از یک build پرهزینه به‌صورت پیش‌فرض نیازمند ظرفیت‌سنجی است.

فایل ورودی صرفاً داده است: نام فایل، header، URL، tag یا فایل همراه حق اجرای shell، تغییر Lua/SQL یا بارگیری تنظیمات اجرایی ندارد. worker پردازش PBF بدون کلید امضا، بدون Docker socket، بدون دسترسی نوشتن به releaseهای سرویس‌دهنده و در حالت عادی بدون خروجی اینترنت اجرا شود.

## ۵. پذیرش منبع، اعتبارسنجی و امضا

**checksum، امضا و کیفیت سه مفهوم متفاوت‌اند.** SHA-256 تغییر bytes را تشخیص می‌دهد. امضای معتبر، انتساب artifact به کلید یا هویت مورد اعتماد را نشان می‌دهد. آزمون کیفیت قواعد پذیرش را می‌سنجد. امضای محلی فایل ناشناس، اصالت منبع OSM یا صحت واقعی عوارض را اثبات نمی‌کند.

دو گواهی مستقل پیشنهاد می‌شود:

- گواهی دریافت/پذیرش: digest PBF، منبع و شواهد آن، محدوده، snapshot، نسخهٔ policy و نتیجهٔ کنترل ورودی.
- گواهی release: digest manifest نهایی شامل artifactها، ابزارهای ثابت و گزارش کیفیت، پس از موفقیت ساخت و آزمون.

امضای خودکار با ابزار استاندارد و کلید کنترل‌شدهٔ سازمان انجام شود؛ الگوریتم یا پروتکل امضای اختصاصی ساخته نشود. سرویس امضا فقط برای digest و policy پذیرفته‌شده مجوز صادر کند؛ signer مستقل با هویت، دسترسی محدود، ثبت ممیزی و سیاست چرخش/ابطال کلید باشد. برای شبکهٔ داخلی، مسیر مبتنی بر کلید سازمانی و verification محلی قابل طراحی است؛ وابستگی به OIDC/اینترنت نباید ناخواسته وارد عملیات شود. Cosign امکان امضای blob با کلید مدیریت‌شده را مستند کرده است. [Sigstore Signing Blobs](https://docs.sigstore.dev/cosign/signing/signing_with_blobs/).

منبع دریافت ایران هنوز مشخص نشده است؛ آن را trusted اعلام نمی‌کنیم. سیاست source allowlist و نحوهٔ کنترل امضای ناشر یا digest دریافت‌شده از کانال معتبر باید پیش از انتشار واقعی تعیین شود. نبود امضای ناشر با سیاست تأیید منشأ و انتقال امن مدیریت می‌شود و در manifest صریحاً ثبت خواهد شد.

## ۶. کنترل‌های پیش از انتشار

کنترل ورودی شامل بازخوانی کامل PBF، نوع snapshot مورد انتظار، عدم history/diff ناخواسته، ترتیب و تکرار objectها، شمار primitiveها، bbox واقعی، timestamp و digest است. دادهٔ قدیمی‌تر به‌صورت خودکار جایگزین جدیدتر نمی‌شود؛ rollback مسیر مجزای ممیزی‌شده دارد. timestamp دریافت فایل به‌عنوان زمان snapshot جا زده نمی‌شود. [Osmium fileinfo](https://docs.osmcode.org/osmium/latest/osmium-fileinfo.html).

ارجاعات way به node و relation به اعضا کنترل می‌شوند. ارجاع ناقص در extract ممکن است وجود داشته باشد؛ موارد بحرانی که ساخت هندسه یا graph را مخدوش می‌کنند مانع انتشارند و استثناهای مرزی فقط با policy شفاف قابل قبول‌اند. checker بررسی relationها باید صریحاً فعال باشد. [Osmium check-refs](https://docs.osmcode.org/osmium/latest/osmium-check-refs.html).

کنترل پس از ساخت:

- تطبیق شمار و digestهای معنایی دادهٔ خام با PBF، حفظ tags و ترتیب روابط؛ نمونه‌برداری به‌تنهایی اثبات حفظ کامل نیست.
- گزارش tagها و relation typeهای ناشناخته، عوارض فاقد هندسه و علل آن‌ها؛ نرخ رد/تبدیل هندسه نسبت به نسخهٔ قبلی.
- اعتبار هندسه و SRID، شاخص‌ها و آمار planner؛ گزارش هر repair به‌جای تغییر خاموش اصل داده.
- coverage matrix برای لایه‌های مورد توافق: راه‌ها، ساختمان، آب و ساحل، landuse، مرزها، مکان‌ها، POI و سایر دسته‌های تعیین‌شده.
- آزمون tile قابل decode، خواص مورد انتظار، پیوستگی مرز tileها، z-order پل/تونل و generalization؛ انتخاب نمونه در چند شهر و منطقهٔ ایران، نه فقط مرکز bbox.
- جست‌وجو و reverse فارسی/انگلیسی، نام/شمارهٔ فارسی، مسیر هر پروفایل پشتیبانی‌شده، یک‌طرفه، منع گردش و محدودیت دسترسی در fixtureهای معلوم.
- تطبیق هویت همهٔ موتورهای release با artifactهای ثبت‌شده؛ نام کانتینر یا timestamp به‌تنهایی اثبات هویت قوی نیست.
- اختلاف آماری با نسخهٔ قبلی برای تشخیص افت شدید حجم/پوشش، زمان عقب‌رفته یا جهش غیرعادی؛ thresholdها وابسته به منطقه و baseline هستند.
- آزمون بار هم‌زمان سرویس‌دهی و ساخت، مرورگر واقعی و probe از مسیر عمومی gateway؛ warm-up کنترل‌شدهٔ cache و connectionها.

نسخهٔ عادی پس از عبور همهٔ gateهای الزامی و امضا خودکار منتشر می‌شود. anomaly به REVIEW_REQUIRED می‌رود و نسخهٔ فعلی ادامه می‌دهد. خطای سخت یا امضای نامعتبر FAILED/REJECTED می‌شود و با «تأیید ساده» از کنترل امنیتی عبور نمی‌کند. نخستین release بر اساس policy اولیه و fixtureها ارزیابی می‌شود؛ baseline قبلیِ ساختگی ندارد.

## ۷. انتشار بدون توقف و حفظ نسخهٔ نشست

واحد انتشار، یک دیتابیس یا backend سراسری با نام current نیست. برای R2 مجموعهٔ مستقل PostGIS، tile، graph، index، POI و assets ساخته می‌شود؛ R1 در این مدت سرویس می‌دهد. رجیستری، نگاشت ثابت هر release_id به endpointهای تأییدشده را نگه می‌دارد. ابتدا R2 در تمام gatewayهای سرویس‌دهنده قابل دسترس و آزمایش می‌شود و سپس default pointer در یک transaction با کنترل نسل/CAS تغییر می‌کند.

نشست تازه release پیش‌فرض را می‌گیرد. نشست موجود به release خودش متصل می‌ماند؛ تمام درخواست‌های نقشه، مسیر، جست‌وجو و POI همان شناسه را دارند. انتخاب نسخه به IP، اتصال keep-alive یا sticky load balancer متکی نیست. lease نشست مجوز مصرف یا جایگزین احراز هویت نیست؛ فقط حق نگهداری موقت نسخه را ثبت می‌کند و renewal آن احراز/محدود می‌شود تا موجب اشغال نامحدود storage نشود.

انتخاب default و ثبت lease نشست در یک transaction با قاعدهٔ قفل مشترک با انتشار و GC انجام می‌شود. در نتیجه نشست هم‌زمان با cutover یک نقطهٔ تصمیم مشخص دارد؛ نشست‌هایی که انتخابشان پس از commit خطی می‌شود نسخهٔ تازه را می‌گیرند. gateway نمی‌تواند از cache قدیمیِ default برای ایجاد نشست تازه استفاده کند. اگر control plane در دسترس نباشد، نشست موجودِ معتبر طبق قرارداد از مسیرهای ثبت‌شده ادامه می‌دهد، ولی ایجاد lease یا حذف نسخه بر اساس حدس انجام نمی‌شود.

نمونهٔ قرارداد، صرفاً طرح اولیه:

```text
POST /api/v1/map/sessions                 -> release_id, lease, expires_at
GET  /maps/<release_id>/styles/light-fa.json
GET  /maps/<release_id>/tiles/<z>/<x>/<y>.pbf
POST /api/v1/map/releases/<release_id>/route
GET  /api/v1/map/releases/<release_id>/search
```

قاعدهٔ دقیق: یک نشست به یک release؛ یک درخواست به یک release؛ همهٔ پاسخ‌ها با هویت همان release. mismatch صریحاً رد شود و هیچ سرویس یا gateway آن را بی‌صدا به current هدایت نکند. هندلر درخواست یک بار release را resolve کند و آن را در سراسر عملیات نگه دارد.

| قبل از ساخت R2 | R1 | — | default=R1 |
| حین ساخت و تست R2 | R1 | R1 اگر وارد شود | R2 غیرعمومی |
| بعد از انتشار R2 | R1 با نشست معتبر | R2 برای نشست تازه | default=R2 |
| پایان پشتیبانی R1 | انتقال کنترل‌شده پس از آماده‌سازی کامل | R2 | R1 پس از drain قابل بازنشستگی |

برنامهٔ وب نباید صرف تغییر health.dataset_id، نشست قدیمی را خودسرانه تبدیل کند. refresh نسخه انتخاب جدیدی است که style، نتایج و overlay را به‌صورت هماهنگ جابه‌جا می‌کند و پاسخ قدیمی را کنار می‌گذارد. نسخهٔ frontend و قرارداد API نیز از نسخهٔ داده جداست؛ سازگاری کلاینت‌های باز در بازهٔ پشتیبانی باید حفظ شود.

cache عمومی شامل release_id، tile/layer contract و گزینه‌های مؤثر است؛ style/theme/language در مسیر یا کلید مربوط لحاظ می‌شوند. منابع ثابتِ یک release URL تغییرناپذیر دارند. bootstrap/default کوتاه‌عمر یا no-store است. cache قدیمی هنگام انتشار سراسری پاک نمی‌شود و 5xx با موفقیت قدیمیِ پنهان‌شده جایگزین نمی‌شود.

gateway هنگام انتشار روشن می‌ماند. اگر ثبت مسیر تازه به تغییر تنظیم Nginx نیاز داشته باشد، reload معتبر و graceful استفاده می‌شود؛ مسیرهای R1 نیز در تنظیم تازه می‌مانند. reload به‌تنهایی عمر نشست چنددرخواستی را حفظ نمی‌کند؛ این کار وظیفهٔ version routing است. [Nginx Control](https://nginx.org/en/docs/control.html).

## ۸. دیتابیس و منابع استقرار

برای هر release دیتابیس مستقل پیشنهاد می‌شود؛ تغییر نام دیتابیس، جابه‌جایی اتصال مشترک همهٔ کاربران یا تعویض view سراسری در لحظهٔ انتشار راه‌حل این نیاز نیست. جدول/دادهٔ release سرویس‌دهنده درجا بازنویسی نمی‌شود.

برای هدف سخت‌گیرانهٔ سرویس‌دهی، build plane و serving plane باید بودجهٔ CPU، RAM، IO و فضای مستقل داشته باشند. ترجیح تولیدی، instanceهای PostgreSQL مستقل برای candidate و نسخه‌های سرویس‌دهنده و جداسازی workload ساخت است. اگر artifact از builder دیگری منتقل/restore می‌شود، انتقال، restore، بررسی و warm-up پیش از READY تمام می‌شود؛ cutover صرفاً انتخاب نسخه است. ساخت روی همان میزبان با quota گزینهٔ استقرار کوچک‌تر است، اما دیسک و kernel مشترک هنوز می‌توانند روی latency اثر بگذارند و نیازمند آزمون‌اند.

ظرفیت باید هم‌زمان نسخهٔ فعلی، نسخه‌های محافظت‌شده، candidate، scratch، indexها، WAL، cache، logs و حاشیهٔ ایمنی را جا دهد. کاهش اولویت فرایند به‌تنهایی تضمین جداسازی IO نیست. پر شدن صف، افت معیارهای سرویس‌دهی یا کمبود ظرفیت ساخت جدید را متوقف/محدود می‌کند؛ نسخهٔ سالم فعلی برای آزادسازی فضا قربانی نمی‌شود.

صفر بودن توقف برنامه‌ریزی‌شدهٔ انتشار هدف قابل طراحی و آزمون است. ادامهٔ سرویس در خرابی میزبان، دیسک یا دیتابیس به HA، افزونگی و backup جداگانه نیاز دارد؛ Blue/Green روی یک VM این ویژگی را به‌تنهایی ایجاد نمی‌کند. Kubernetes پیش‌شرط این معماری نیست؛ انتخاب orchestrator تابع تعداد گره‌ها و نیاز عملیاتی خواهد بود.

## ۹. نگهداری، نشست و حذف امن

حفظ نسخه برای نشست نامحدود با سقف محدود storage قابل جمع نیست. باید عمر مجاز نشست، تمدید، حداکثر زمان پشتیبانی release قدیمی و زمان اطلاع‌رسانی مشخص باشد. پس از پایان این بازه، انتقال هماهنگ یا پیام انقضای صریح انجام می‌شود؛ درخواست قدیمی بی‌صدا روی دادهٔ جدید اجرا نمی‌شود.

سیاست نمونه برای بررسی: آخرین سه release موفق به‌علاوهٔ هر نسخهٔ محافظت‌شده. سه عدد قطعی نیست و نسخه‌های محافظت‌شده می‌توانند موقتاً شمار را بیشتر کنند. حفاظت شامل current، مقصد rollback تضمین‌شده، lease معتبر، درخواست درحال اجرا، job وابسته و pin مدیریتی است. آرشیو آفلاین با نسخهٔ گرم و آمادهٔ rollback متفاوت است.

چرخهٔ GC:

1. توقف پذیرش نشست تازه/تمدید فراتر از پنجره برای نسخهٔ در حال drain.
2. پایان leaseها با سیاست مصوب؛ registry و شمار درخواست‌های فعال با کنترل race بررسی شوند.
3. ثبت RETIRED و مهلت ایمنی؛ سپس با قفل و fencing و بررسی دوباره وارد DELETING شود.
4. بستن مسیرها و poolهای همان release و حذف فقط volume/DB/artifactهای مدیریت‌شدهٔ بدون reference.
5. حفظ manifest، امضا، گزارش و tombstone برای ممیزی؛ حذف ناتمام پس از crash قابل ادامه باشد.

حفاظت با کنترل هم‌زمانی مشترک میان ایجاد/تمدید نشست، انتشار و GC enforce شود؛ فقط تکیه بر last_access یا گزارش کانتینر کافی نیست. خرابی control plane یا ناتوانی در تشخیص reference باعث توقف حذف می‌شود. اگر نسخه‌های محافظت‌شده در بودجه جا نمی‌شوند، import جدید به BLOCKED_CAPACITY می‌رود.

برای صرفه‌جویی، PBF بر اساس digest یک بار نگهداری شود، فایل‌های موقت پس از checkpoint معتبر پاک شوند و cache/log سقف داشته باشند. hardlink به فایلی که بعداً writable است راه امن snapshot نیست. حذف نسخه‌های قدیمی جای سیاست backup و restore آزموده‌شده را نمی‌گیرد.

## ۱۰. rollback و بازیابی

پیش از commit انتشار، خطای candidate هیچ تغییری در default فعلی ایجاد نمی‌کند. پس از commit، خطای gate عملیاتی می‌تواند default را به نسخهٔ قبلیِ آماده برگرداند. در rollback معمول، نشست‌های R2 فقط در صورت سالم و مجاز بودن R2 ادامه می‌دهند؛ در خرابی شدید یا خطر امنیتی R2 قرنطینه و انتقال صریح مدیریت می‌شود. حفظ نشست روی نسخهٔ خراب بر امنیت و صحت مقدم نیست.

jobها، registry، publish generation و رویدادها بادوام و قابل recovery هستند. انتشار موازی، worker مرده با lease منقضی، restart gateway و crash وسط GC باید نتیجهٔ قطعی و idempotent داشته باشند. شناسهٔ request/release/job در metrics و audit به هم متصل است و مختصات یا متن جست‌وجوی حساس بی‌دلیل ثبت نمی‌شود.

## ۱۱. معیار پذیرش و ترتیب اجرای پیشنهادی

معیارهای الزامی:

- همهٔ primitives ورودی و tags/روابط طبق قرارداد قابل تطبیق باشند؛ حذف‌های خاموش صفر.
- خطا یا anomaly ورودی نتواند release سالم را کنار بزند.
- کاربر R1 حین ساخت و انتشار R2 مجموعهٔ هماهنگ R1 را ببیند؛ نشست تازه پس از commit R2 را بگیرد.
- درخواست‌های درحال اجرا و منابع نسخهٔ قبلی هنگام انتشار قطع نشوند؛ خطای ناشی از تعویض برنامه‌ریزی‌شده در آزمون هدف صفر باشد.
- اهداف latency/throughput و مصرف منابع پس از تعیین workload و benchmark مشخص و هم در بار عادی و هم import هم‌زمان رعایت شوند.
- سلامت از gateway عمومی، مرورگر واقعی و موتورهای واقعی آزموده شود؛ HTTP 200 به‌تنهایی اثبات صحت لایه‌ها نیست.
- rollback، crash recovery، ورودی تکراری/ناقص/دستکاری‌شده، کلید نامعتبر، stale snapshot، کمبود دیسک، lease هم‌زمان GC و عدم دسترسی control plane آزموده شوند.

ترتیب اجرا:

1. نهایی‌سازی source trust policy، مدل خام/مشتق، پوشش feature، قرارداد نشست و معیارهای عملیاتی.
2. نمونهٔ محدود Martin/PostGIS و benchmark روی PBF ایران؛ خروجی این مرحله انتخاب ابزار و ظرفیت مورد نیاز است.
3. ایجاد pipeline staging و QA بدون تغییر سرویس فعلی؛ مقایسهٔ عملکرد و صحت با baseline.
4. اضافه کردن registry، version routing، نشست و انتشار چندنسخه‌ای و تمرین rollback.
5. ورود خودکار، امضا، گردش REVIEW_REQUIRED، retention و GC ایمن.
6. آزمون پذیرش و مهاجرت اولیه: معماری جدید کنار نسخهٔ فعلی روشن شود و نشست‌های قدیمی تا پایان بازهٔ مصوب پشتیبانی شوند؛ سپس تغییر ورودی با قابلیت بازگشت انجام شود.

اجزای بالا باید یک طرح کامل را دنبال کنند، اما در تغییرات کوچک و قابل بازبینی تحویل شوند. سناریوهای خارج از دامنه مانند satellite، terrain، ترافیک زنده یا پشتیبانی کامل همهٔ معنای tagهای OSM تنها با تعریف صریح نیاز، داده و آزمون به دامنه اضافه می‌شوند. عبارت «full feature» جای ماتریس قابلیت و معیار پذیرش را نمی‌گیرد.
